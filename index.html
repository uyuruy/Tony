Case Study: AI Meeting Intelligence

UK medical client • Meeting operations • Google Workspace + Claude API

The Problem

Important decisions, actions, owners, and follow-ups were buried inside meeting recordings. Reviewing every recording manually was repetitive, and the useful output still had to be turned into a shared operating record.

The Workflow I Built

  • Drive intake: recordings entering a defined Google Drive workflow are picked up automatically by Google Apps Script.
  • Claude processing: the recording content is passed to the Claude API against a structured extraction prompt.
  • Structured JSON: the response returns decisions, action items, owners, and minutes in a predictable schema.
  • Shared operating record: validated outputs are written into a central Google Sheet for review and follow-through.
  • Human review: nothing is treated as final until a person validates the output.

Why the Design Matters

The goal was not to generate another summary. It was to turn an unstructured meeting artifact into operational data that could be reviewed, assigned, and acted on. The workflow separates AI extraction from human approval so automation speeds up the repetitive part without replacing judgment.

Case Study: AI Intake & Decision Routing

Internal candidate intake and triage • Notion + Apps Script + Claude API

The Problem

New candidate records needed to be reviewed against the same criteria, assigned a clear status, and moved to the right next step. Doing that record by record made the intake process slower and more dependent on manual follow-up.

The System I Built

  • Structured intake: candidate records are stored in Notion with consistent fields and a pending status.
  • Timed processing: Google Apps Script reads eligible records automatically.
  • Rubric-based evaluation: Claude evaluates the record against a defined set of criteria rather than an open-ended prompt.
  • Decision routing: the structured result determines the appropriate next action and updates the record.
  • Review controls: edge cases can be surfaced for human review rather than allowing the model to guess.

Operating Principle

AI is useful here because the decision criteria are explicit. The workflow keeps the rubric outside the model, asks for structured output, and uses that output to move the record through a defined process. That makes the automation easier to audit and easier to change when the operating rules change.

Case Study: Reusable AI Triage Engine

Reusable intake-to-routing pattern • Four operating use cases

The Pattern

Different service workflows had the same underlying problem: a person had to read every incoming request, decide what kind of request it was, and route it manually. I built one repeatable architecture and adapted the rules for each use case.

  • Intake: Jotform captures the structured request.
  • Orchestration: Zapier passes the record into the classification workflow.
  • AI classification: Gemini returns a structured result against the use-case rules.
  • Validation: the model output is checked against the expected schema before another system consumes it.
  • Routing: Airtable and Asana receive the classified record and next action.

Where It Was Reused

  • Tutoring intake

Case Study: AI-Powered Market Risk Analysis

Project Overview

An autonomous, serverless workflow I designed and built from scratch to automate market risk analysis. It fetches daily news headlines, uses Google's Gemini AI to produce a structured risk assessment, and distributes the intelligence to a live Airtable dashboard and a proactive Asana task system.

My Role & Architecture

As sole architect, I coded the end-to-end pipeline in Google Apps Script. The workflow:

  1. Triggers daily to fetch news from pre-configured RSS feeds.
  2. Sends headlines to the Gemini API within an engineered prompt returning strict JSON.
  3. Distributes structured data via API to an Airtable dashboard and an Asana project for proactive alerts.

Live System View

The live Airtable database below is the central hub for the daily, AI-generated risk analysis.

Key Challenges & Resolutions

  • API Errors (404s & 403s): Resolved model rejection and access errors by iteratively testing model versions and re-configuring token permission scopes.
  • Data Parsing Failures: Implemented robust regex extraction to guarantee clean JSON, overcoming AI response formatting inconsistencies.

Psalms Laundry – Systemizing the Operating Layer

Operations Manager • Subscription laundry & cleaning • Lagos • Jul 2024–Mar 2026

The Operating Problem

The business had grown around manual tracking, a large spreadsheet, and too much interpretation in day-to-day work. Pricing, unit counting, order status, quality control, and reporting needed a clearer operating layer. As Operations Manager, I rebuilt the process around structured data, defined rules, and staff-facing workflows.

Systems I Built

  • Live mobile operations app: AppSheet forms for pickup, sorting, and quality control, with four automations driving order status.
  • Financial model: a 31-tab workbook with monthly P&L reporting and a weighted piece-count pricing model built from unit economics.
  • SOP library: documented intake, washing, quality control, packaging, delivery, complaints, and pricing rules.
  • Customer and order database: five linked tables connecting customers, orders, line items, pricing, and operating records.

A Failure That Changed the System

When ambiguous unit counting contributed to losing a subscriber, I treated it as a process-definition problem rather than a staff problem. I built a weighted piece-count system and a 37-item counting guide so the team had one consistent rule set for pricing and order records. That same principle shaped the rest of the operating system: make the rule explicit, put it into the workflow, and reduce the amount of work that depends on memory.
